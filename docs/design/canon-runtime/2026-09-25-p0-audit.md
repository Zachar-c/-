## 4. Evidence 稳定性发现（任务要求专项）

- E-ID `E:V{段}-{6位行号}` 完全依赖仓库根 `蛊真人-clean.txt` 绝对行号；该文件**不入 Git、无任何 hash/version 登记**（全 wiki grep sha256/hash/version = 0）。
- `check.ps1` check9 只校验"段号↔行号区间"一致性，不打开原文、不比对行内容；行号正确性最终靠人工与原文不动。
- wiki 的 `source:source/蛊真人-clean.txt` 是逻辑 URI，实际文件在仓库根（已登记债务）；lore_engine 的 manifest 另钉了一份 `分支：六卷精编版/蛊真人-clean.txt` 的 sha256（口径未与 wiki 统一）。
- **处置**：编译器在 manifest 里记录 source_id/source_version(sha256)/行数/编译时间；原文缺席或 hash 变化时报错，不静默沿用旧 E-ID。不改 Wiki Schema。

## 5. 编译器可行性

有利：1374 个 E:V 锚点、263 个 EVT 定义、25 个 ST 定义、43 条 CAN 定义＋108 条页内规则行（REF/KM/DM/PR/TRIB/VEN/DRM）；机器可读载体是 Markdown 表格（ID 固定首列）；frontmatter 是合法 YAML；已有 check.ps1 门禁与 section-index.md 段表。

难点（P2 必须显式处理）：
1. frontmatter 两代并存（71 概念页：47 页 v2 八键 / 24 页 v1 四键）——解析器容忍缺省。
2. 区块标题 62 种变体——**按"表格首列 ID 模式"定位对象，不按标题定位**。
3. 双注册域＋两套证据语法：CAN-*（canon-index，`` `蛊真人-clean.txt:行号`，等级 ``）与页内规则行（E:V 语法）需各写一个解析器再归一。
4. E-ID 短格式漂移约 15 处、`ST-` 正则会被 `CAN-BEAST-*` 子串假阳性（需左边界）。
5. 无 ID 规则表（如 primeval-essence.md 规则表）——运行时生成确定性 ID（`{page-slug}-NNN`），不回写 wiki。

可复用资产：lore_engine 的 `source_manifest.py`（sha256 指纹＋路径逃逸防护）、`validator.py`（引文对齐＋CANON/INFERRED/ADAPTATION/GAME_ORIGINAL 四分类）、`seeds.py`/`pipeline.py`（幂等导入与断点续跑）；build_data.mjs 的 JSON＋sha256 contentVersion 范式。
