# 蛊虫关系图谱执行约定

先读 [README](README.md)。这是用户授权的关系研究目录，不是原著 Wiki 或游戏运行规则。

- 用户要求每新增一只蛊都考虑与此前蛊虫的关系。新增时完整扫描现有蛊池，按 README 的新增流程提交节点、具体关系/候选以及暂不连边的理由；不得只追加孤立名称。
- 用户后续明确：最终标准是可玩、有趣、有意义的蛊虫构筑。每只新蛊须回答它改变哪套力量循环、实际操作、资源或敌人答案，以及何时应该拒绝它；同标签、套装数量和伤害增加不等于构筑突变。实际玩法实现与验证入口是现有 [问真 Web 实验室](../../../game/wenzhen-web-lab/lab.html)；本目录不维护玩法原型，`playable-builds.md` 仅存历史验证记录。自动检查不能替玩家认定有趣。
- 原著依据优先消费 `lore/wiki/`，有缺口再查 `source/蛊真人-epub-canon.txt`。本局材料和会话助手的推演不得升级为原著事实。
- `graph.json` 是此研究的唯一关系数据入口；修改后运行 `python3 docs/design/gu-relations/tools.py --self-test`。新增节点必须补 `admission`，列全登记时此前的蛊 ID，并以具体关系或有理由的暂不连边分组覆盖它们。
- 概念只能发现候选，不证明可以催用、合炼、逆炼、替代或叠加。完整合炼输入保留在同一条关系内；未记录辅料/过程时 `process_complete` 保持 false。谱系不能伪装成完整蛊方。
- 留存力量、双眼改造、伤势等使用状态单列；材料、状态与未具名需求不计入蛊数量。同名但来源不同的月痕记录不得合并效果和转数。
- 在图谱已有且互不冲突的工作流中，可按用户要求委托取证或独立审查；主代理负责共享数据修改与最终验收。
- 保留其他任务的未提交改动。图谱扩展不自动修改 Wiki、产品范围、数值或游戏数据；研究候选不是已经通过评审的玩法。

- 2026-10-03用户裁决：功能参考成熟肉鸽游戏，实现与验收基于网页。当前唯一主实现为问真 Web 实验室 `game/wenzhen-web-lab/lab.html`；旧网页原型与 Windows 模组已退役，历史验证结论见 `playable-builds.md`。不据此宣称原著机制已全部实现。
