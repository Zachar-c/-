日期：2026-10-02。性质：源层关系研究，承接用户“以原著 Wiki 为基准，以会话讨论为思考，每新增一只蛊都考虑已有关系”的授权。首批从月系分叉、力道协同、金睛与金龙两个子体系、本局跨道炼制开始。这里的设计候选未接入产品规则。

当前路线（2026-10-03用户裁决）：**以网页端作为实现与确认基础，复用成熟游戏的功能思路，技术留在网页端。** 唯一主实现是现有[问真 Web 实验室](../../../game/wenzhen-web-lab/lab.html)；本目录不再维护第二套玩法实现。旧网页原型和 Windows 模组源码已清理，曾经的机制验证结论保存在[历史试玩记录](playable-builds.md)。这些记录只说明当时执行过哪些检查，不代表原著机制已完整实现或玩家趣味已验收。

用户后续纠正验收目标：关系数量不是成功标准，必须形成可玩、有意义、有趣的蛊虫构筑；并选择先做可试玩样本，再决定接入正式游戏。当前推进入口是[构筑样本与验收](playable-builds.md)。首批关系检查只证明研究登记，不证明游戏体验完成。

当前登记 **40 条蛊虫记录（31 条原著、9 条本局）**、12 个状态/材料/未具名功能需求、48 条关系。新增九叶生机草与生机叶，记录本体产叶、叶片消耗与疗伤间隔；网页时间和经济映射仍单列为设计候选。它是第一批可扩展数据，不是已经完成约1000只蛊，也不将约1000只冻结为首发数量。两份同名月痕来自不同来源，单独记账。

## 两种身份，三层证据

蛊的道属与转数回答“它是什么”；功能、作用对象、使用条件与代价回答“它能解决什么”。后者帮助跨道发现接口，但不是同标签自动兼容规则。

| 维度 | 记录方式 | 禁止推论 |
|---|---|---|
| 原著明确 | `basis=canon`，附 Wiki 落点、当前 EPUB 章段和段落哈希 | 不从游戏分类或会话助手判断倒填原著道属 |
| 本局记录 | `basis=session`，附附件行段与哈希 | 附件名有“Canon”也不等于原著事实 |
| 设计候选 | `basis=design`，`verification=unresolved/inferred` | 概念匹配不能直接形成可用配方或杀招 |
| 独立核验状态 | `verification=attested/inferred/unresolved` | 一个节点原著存在，不代表它的所有关系都属原著 |

图中的“月系”“力道”等分组用于阅读。月光蛊原著道属未明文；月痕/月旋转数不据存量总表填死。金风送爽本体四转，“堪比五转”是效果评价。未知 `rank` / `path` 留 null，备注保留原因。`provides` / `accepts` 是我们对已记效果的概念索引，不能泛化为通用作用接口。

原著月痕是月光＋痕石的射程路线；本局月痕记录了主攻和本命母体用途。两个 ID 分别为 `moon-ray` 和 `session-moon-ray`。R025 保存对照与未知，不声称两者可互换。

R032 是本局“发生过什么”的综合记录，不是可以照表执行的完整蛊方。月胎虫蜕提供结构启发，同步辅蛊是未具名过程工具；主辅材料的完整清单、用量和最终去留未保存。关系中 `input` / `output` / `auxiliary` / `state` / `participant` 区分作用；R032另分候选辅材、结构参考、启发、过程工具和正式干预，`process_complete=false` 防止把片段误当整方。`quantity=null` 表示用量未记录；只在有明确证据时填入只数，材料/状态不默认一单位。

## 每新增一只蛊的流程

1. **定身份与边界。** 查已有 ID、别名、原著/本局版本和具体使用阶段；道属、转数或功能证据缺失就留未知。先排除同名仙凡蛊、材料名、杀招名与蛊实体碰撞。
2. **写真实功能。** 记录作用对象、输出/输入状态、启动条件、供养/真元/获取/操作代价和限制；未测数值不补造。功能无法确认时仍可保留实体和明确未知，不能根据名字发明作用。
3. **扫描全部此前蛊。** 候选工具遍历现有蛊池；分别考虑合炼/逆炼、同催、时序、状态前置、资源中介、替代取舍、结构借用和负向冲突。同流派不是唯一搜索范围。
4. **逐组作结论。** 能被来源支持的关系落正式记录；仅有功能相似性落设计候选；其他此前节点分组写“本批缺少哪类证据，因此暂不连边”。不得为凑连接数造关系，也不能把暂不连边写成永久不兼容。
5. **补增量审查。** `admission.prior_gu_ids` 必须列全登记时此前的蛊；`relation_ids` 与有理由的 `no_link_groups` 合起来恰好覆盖它们。首批为回顾式审查，登记顺序不代表故事获取顺序。
6. **核验并同步。** 跑来源和结构检查，独立复核关键机制，更新可读窗口及本批变更记录。发现原著/Wiki冲突先标未知再回查，不静默升级推演。

新增蛊还须经过[构筑验收](playable-builds.md)：明确它服务的力量循环、加入前后的实际操作或资源差异，以及玩家拒绝它的理由。概念命中或“凑齐套装”的布尔值不能替代正常获得后的实战对照；数值补强不冒充构筑突变。

接受一只蛊没有“至少两条连边”的指标。验收看它是否给玩家带来具体选择：让旧蛊换用法、将历史投入变成新收益、为别道提供结构、补缺口或引入新的真实取舍。世界填充蛊可以暂不连边，但必须保存考虑过哪些对象、为什么目前没有依据。

关系类型可组合，但不可混成一句万能“协同”。配方是一条整组关系；谱系、战斗顺序、具体战例、身体状态、价格可得性和候选替代分别保留条件。只在真正需要时增加新的概念，不先凑够50–100个标签。

## 运行与核验

在仓库根目录：

```bash
python3 docs/design/gu-relations/tools.py --self-test
python3 docs/design/gu-relations/tools.py --candidates split-nest
python3 docs/design/gu-relations/tools.py --render /absolute/task-owned/gu-relations.html
node tools/docs-lint.mjs
```

`--candidates` 可用一个已登记但尚未完成 `admission` 的新增节点，扫描其他全部蛊；它只提建议，不写关系。先补人工审查，再运行完整验证。`--render` 只生成对话中可浏览的 HTML 片段；从 `graph.json` 插入数据，不增加另一份手工事实。

源码或附件变化会被段落/行段哈希发现；应回到来源检查受影响事实，再更新证据，不能只改哈希让检查变绿。检查通过证明来源与登记完整，不能替代机制审查或玩家实测。
