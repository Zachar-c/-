## §2 范围与重点

**做什么**：让剑道在战斗里**真的像剑道**——有「势」（剑意）、有**代价**（侵蚀）、有**出手顺序策略**
（先铺势后出剑）、40 只蛊**彼此可区分**（不再同 role 同一效果）。

**重点（按价值排序）**：
1. **T2（attack 显式化 + 支援分档）** —— 唯一能立刻产生"剑道手感"的改动，也是 F4 的落点。
2. **T1（式数值表）** —— 它是 T2/T3/T4/T5 的共同输入，且是**唯一能在写数据前被审阅**的产物。**先出表再写库**。
3. **T6（侵蚀代价）** —— 让「叠满再放」不是无脑最优；红线敏感，成本必须可见。
4. **T5（10 只辅助蛊的归宿）** —— 不解决就永远是 25% 的死数据。
5. **T7（契约测试）** —— 没有它，40 只手写数据的回归风险不可控。

**明确不做**：
- ❌ 不动 `v1_battle_resolver.gd` / `content_catalog.gd` 的任何逻辑（本批是纯数据 + 1 个新测试文件）
- ❌ 不做跨流派克制倍率（规格 §2.3 红线）
- ❌ 不引入抽牌/手牌/剑意抽牌类设计（卡牌红线）
- ❌ 不动 `gu_instances` 账本、不动存档结构
- ❌ 不改 starters 名单（`schools.json` 不变；T2–T6 只在 `gu.json` 改被引用的定义）
- ❌ 不为其它 19 个流派顺带补数据（**剑道是试点**；跑通后再复用同一套流程）

## §3 必须遵守的约束条件

**引擎侧（本轮实测，写数据前必须知道）**
1. **显式 `v1_effect` 无转数成长**（F1）⇒ 逐 rank 写 `amount`；漏写即产生"rank5 不如 rank1"的静默失衡。
2. **`status` 只能写 `marked` / `bound`**，且**两者都不参与伤害**（F2）⇒ 不要用 status 表达"破防/减伤"。
3. **`buff` 只影响 `basic_attack`**（F3）⇒ 不要用 buff 表达"给剑招加伤"。
4. **`support_school` 只惠及本回合后续同流派蛊**（F4）⇒ 支援蛊必须在主力蛊**之前**出手才有意义；设计要按此排序。
5. **`shift` / `status` 不随转数放大**，`strike` / `shield` / `heal` 才会（`RANK_SCALED_KINDS`）。

**项目红线（违反即回退）**
6. 代价**真实结算且执行前可见**；**禁止静默致死**——`life_cost` 路径必须保留预检与明确提示。
7. 数值全部落 JSON 并通过 Schema 校验；**不散落硬编码**。
8. 道标签**不产生全局克制倍率**；差异化只能落在己方资源循环、结算方式、代价结构。
9. 蛊按实例结算；**无蛊槽、无持有上限**。
10. 禁止新增局外数值成长（图鉴是唯一跨局解锁）。
11. **行为保持**：T2–T4 显式化前后伤害逐只相同；若发现不同，按 §0-F1 的口径修正，**不得改断言**。
12. 改动 UI/快照键/命令面须回写契约——**本批应不触发**；若触发则同步 `docs/contracts/`。

**流程约束**

## §5 执行顺序

```
T1（式表，先审阅）
  └─→ T7（先建契约测试，允许红）
        └─→ T2（attack 15，核心）→ T3（def/heal 10）→ T4（move 5）
              └─→ T5（10 只辅助蛊裁定）→ T6（侵蚀代价）
                    └─→ 批次 1 提交 + 全量回归
                          └─→ T8（跨回合剑意）→ T9（杀招 +2）→ 批次 2 提交
                                └─→ 批次 2b：T10（剑道道痕）→ T11（兼修代价）
                                      → T13（元石→真元）→ T14（杀招矩阵 + reveals）✅ 已完成
                                      （T12 已删除）
                                            └─→ 暂停：剑道是否"好玩"由试玩决定 → 再议 P2（T15/T16）
```

**为什么把 T10–T14 放在 P0/P1 之后而不是之前**：它们是**世界观整合**，依赖"剑道机制已经存在"才谈得上接线
（例如 T12 要比较 `sword_intent` 与 `mark_sword` 两条数值，得先有 T8）。
但**不要把它们无限推迟**——它们是把剑道从"一组数值"变成"一个流派"的那一步。

**分批理由**：T1 先出表是因为 40 只手写数值**不可盲写**；T7 先于 T2 是 TDD 纪律；T8 必须在 P0 之后，
因为它依赖"剑意存在且可感知"这一前提；P2 必须在**试玩验证 P0/P1 之后再谈**，否则是在为未验证的玩法扩引擎。

## §6 风险与回滚

| 风险 | 说明 | 应对 |

| **静默转数失衡** | F1 的坑：漏写 rank 加值 ⇒ rank5 与 rank1 同伤害 | T7 用例 2 直接钉死 |
