# 小说到游戏：蛊世界知识引擎设计

> 日期：2026-08-26  
> 状态：已获用户逐节批准，待书面规格复核  
> 首期范围：阶段 0（基准校准）与阶段 1（可验证纵向闭环）

## 1. 目标与边界

本系统的目标不是把《蛊真人》缩写成剧情关卡，也不是先挑少量知名设定套入卡牌肉鸽。目标是先把工作区约 700 万字小说正文编译成一套机器优先、可查询、可推理、可验证的蛊世界知识模型，再由独立适配层将该模型编译成 Roguelike 游戏内容。

```text
小说原文
  -> 蛊世界知识引擎
  -> 可运行的世界规则候选
  -> Roguelike 人生模拟
```

第一次转换追求复刻级还原，第二次转换才追求游戏性。原著知识不得因当前玩法不需要而在提取阶段被删除、改写或降级；游戏为可玩性增加的数值、触发方式和补全内容不得回写原著知识库。

### 1.1 内容优先级

- 设定优先，剧情其次。
- 设定覆盖命名对象，也覆盖没有专名的社会、生存、经济、权力和信息运行机制。
- 剧情主要用于提供人物、势力和时代背景，以及验证设定如何实际运转的案例。
- 知名台词可派生为加载画面或题记素材，但不承担规则裁决。
- 哲学、善恶观、自由意志等主题保留为可追溯的角色主张、情节推论或整理者解读，不在首期抢占硬设定工程的优先级。

### 1.2 权威语料边界

- `分支：六卷精编版/蛊真人-clean.txt` 是客观设定的最高权威正文。
- `分支：六卷精编版/《人祖传》.txt` 作为蛊世界内部典籍独立收录，默认属于 `in_world_lore`；其内容在正文现实中得到验证后，才另行生成客观事实。
- 工作区读书笔记、`肉鸽设计-原始数据/`、Wiki、百度百科、贴吧整理等都是候选与查漏来源，不能单独把结论升级为原著事实。
- 原文中的定量数据与“极少、通常、数倍、近乎不可能”等定性尺度均须提取。原著未给出的概率和数值不得在原著层估算。

## 2. 总体架构

系统采用“独立原著知识库 -> 后置游戏适配层”的结构，以原子事实、证据和案例为核心，而不是以百科词条为核心。

```text
小说正文 ------------------+
《人祖传》及世界内传说 -----+-> 原文索引与证据库
二手资料、读书笔记 ---------+         |
                                      v
                              多路候选发现
                         +---------+---------+
                      词典反查   全文扫描   随机盲审
                         +---------+---------+
                                      |
                                      v
                         原子断言 / 运行机制 / 案例
                                      |
                                      v
                         后文裁决、冲突过滤、证据聚合
                                      |
                                      v
                            蛊世界最终知识模型
                         /            |             \
                    复杂查询      百科与报告       待核验清单
                                                       |
                                                       v
                                                游戏适配层
```

### 2.1 四层数据边界

1. **原文层**：保存文件指纹、卷章、段落、字符范围、文本块和短引文；原文只读。
2. **证据层**：保存对象候选、原子断言、运行机制、实际案例、支持证据、反驳证据、适用条件和尺度。
3. **最终知识层**：暴露同一设定的唯一当前版本，以及严格分离的推论、未知与世界内传说。
4. **游戏适配层**：引用最终知识 ID，定义卡牌、敌人、节点、数值、抽象和原创补全；不得反向污染前三层。

### 2.2 存储选择

第一版使用 SQLite 作为唯一结构化真值，承载实体、断言、证据、案例、机制、推论、任务和裁决记录，并启用全文检索。语义向量索引、模型缓存、Markdown 百科、JSON 报告和游戏候选表均为可重建派生产物。

不在第一版引入独立图数据库。关系通过规范化表和递归查询表达；只有在真实查询负载证明 SQLite 无法满足后，才评估迁移。

## 3. 高召回发现管线

分类是发现后的视图，不是发现前的搜索边界。任何管线发现新对象、新关系或新知识类型，都应进入共享候选池并触发全文反查。

### 3.1 原文预处理

- 确定性识别卷、章、段落和可用的场景边界。
- 为文本块生成稳定 ID、字符范围、内容哈希和相邻上下文引用。
- 建立字面全文索引、中文检索索引和语义向量索引。
- 检测章节解析异常、重复文本、乱码、截断和未索引区域。
- 原文变化时只重算受影响的块和派生记录。

### 3.2 百科驱动反查

从二手资料与现有整理物中提取名称、别名、称号、关系、能力、配方、地点、势力、争议说法和可能出处。这些内容只进入候选队列。系统必须回查正文中的支持、限制、反例和后文修正；找不到正文依据时保持未确认状态。

### 3.3 全文开放扫描

全文按带重叠上下文的场景块批量分析。发现模型采用开放输出，寻找：

- 新对象、别名和身份变化；
- 明示规则、条件、代价、限制、例外和尺度；
- 无专名的社会运行机制；
- 具有独立设定价值的实际案例；
- 角色主张、传闻、世界内传说和隐含推论；
- 当前 Schema 无法表达的新知识类型。

不同发现视角共享结果与缓存，避免一个万能提示词形成稳定盲区，也避免对同一文本机械生成多份摘要。

### 3.4 规则语言与结构扫描

程序优先定位定义、条件、限制、尺度、因果、变化和认知修正等高价值表达，再交由模型判断。种子模式包括但不限于：

- 定义：`所谓`、`称为`、`分为`；
- 条件：`只有`、`必须`、`除非`、`需要`；
- 限制：`不能`、`无法`、`最多`；
- 尺度：`通常`、`极少`、`数倍`；
- 因果：`因此`、`代价`、`反噬`；
- 变化：`晋升`、`炼成`、`损毁`、`取代`；
- 修正：`原来`、`并非`、`真正`。

模式只用于召回，不用于直接生成事实。

### 3.5 图谱递归扩张

每个已发现对象或关系自动派生反查任务：别名、组成、来源、拥有者、使用者、能力、条件、消耗、喂养、炼制、克制、协同、失败、反噬、地域、势力、交易与历史影响。新发现继续递归，直到新增对象、关系和例外连续多轮收敛。

### 3.6 独立盲审

审计流程在不知道当前词表和分类的情况下抽取随机原文片段，独立识别其中的世界知识、知识库遗漏和 Schema 缺口。盲审发现会生成专项补扫规则，防止主管线共享同一种偏差。

### 3.7 共享与效率

- 原文只切块、嵌入和索引一次，所有发现路径共享。
- 所有模型任务记录输入哈希、模型、提示词版本和输出，命中缓存时不重复计费。
- 先并行发现，再统一实体对齐、去重、证据扩搜和裁决。
- 已确认对象只处理新增证据，不重复做全量分析。
- 扫描强度由新增率、漏检类型、争议密度和影响范围动态调整。

## 4. 证据权重与裁决

系统区分“候选置信度”和“原著确认度”，避免把二手共识误当正文事实，也避免浪费多源重复提供的有效线索。

### 4.1 候选置信度

候选置信度回答“这条说法是否值得投入更多核验预算”。评分因素包括：

- 独立来源簇数量；
- 来源的历史准确率；
- 是否提供可回查出处；
- 多种发现管线是否独立命中；
- 与原文的字面或语义匹配强度；
- 来源间复制相关性与冲突程度。

多个复制自同一源头的页面只能视为一个来源簇。多个模型读取同一段文本、使用近似提示词所得结果也不能伪装成独立证据。

候选置信度影响检索优先级、检索范围、模型预算和人工争议排序。它不能单独生成 `canonical_fact`。

### 4.2 原著确认度

原著确认度回答“正文是否足以支撑这条最终设定”。其核心因素是：

```text
实际情节结果验证
> 可靠旁白明示
> 多个独立案例共同验证
> 角色亲历且与结果一致
> 角色转述
> 角色推测、传闻或谎言
```

二手共识可在正文含糊时参与最佳推断，但不能覆盖明确相反的正文。

### 4.3 后文优先

正文越后通常越权威，但后文优先只在同一对象、同一状态或时期、同一适用条件、同一语义层级且结论不可兼容时用于裁决。

- 人物成长、时代变化、地域差异和规则例外不是前后冲突。
- 后文角色猜测不能自动推翻前文实际情节。
- 确属后期改写时，最终知识层只暴露后文版本；前文仅在内部证据层标记为 `superseded`。

### 4.4 自动确认门槛

一条断言只有满足全部条件才可自动确认：

- 每个关键字段都有正文证据；
- 至少一项强证据，或多项独立且一致的正文证据；
- 已完成名称、别名、语义、共现和后文反证检索；
- 不存在未解释的强冲突；
- 结论没有超出正文断言范围；
- 对象、条件、时期、适用范围和尺度均明确；
- 达到其影响等级对应的确认阈值。

无法满足时使用 `unconfirmed`、`in_world_lore`、`character_claim`、`best_supported_inference`、`conflicted` 或 `unknown`。证据不足但很可能存在的内容保留在待核验层，不进入严格查询、最终百科和游戏适配。

### 4.5 反驳优先

每次自动确认前都必须主动搜索：后文推翻、角色谎言或误判、失败案例、适用条件、地域或境界限制、发生与普遍性的混淆、具体案例被错误泛化等。

### 4.6 影响等级与人工审核

- `critical`：修炼、资质、境界、真元、道痕等底层规则；
- `high`：影响大量对象的炼养用、经济、组织和社会机制；
- `medium`：某类对象、地域或势力的共享规律；
- `local`：单一对象的局部描述。

系统尽量自动化。只有重大争议、无法裁决的高影响冲突和质量异常提交用户审核；普通对象满足强证据门槛后自动确认。

## 5. 核心知识模型

### 5.1 对象 `entity`

对象用于稳定指认蛊虫、蛊方、杀招、材料、资源、人物、势力、地点、秘境、境界、资质、制度及无专名机制。对象只承载身份、别名和类型，不把全部知识塞入一个大对象。

### 5.2 原子断言 `claim`

每条断言只表达一个最小结论，并保存主体、谓词、客体、条件、适用范围、时期、尺度、断言类型和状态。

尺度至少区分：

- `always`：确定规则；
- `usually`：原著明确的普遍倾向；
- `possible`：只证明可以发生；
- `rare`：原著明确表示少见；
- `unknown_frequency`：已有案例但原著未说明概率。

### 5.3 证据 `evidence`

证据绑定原文块、短引文、卷章、字符位置、原文顺序、叙述类型、支持方向、适用条件、来源簇和评分明细。所有引文必须能逐字回到当前原文。

### 5.4 案例 `case`

案例表达：

```text
前置状态 -> 参与者与资源 -> 行动 -> 代价 -> 结果 -> 失败原因或例外
```

系统保存所有具有独立证据价值的表现类型，包括首次能力展示、具体消耗或条件、失败、反噬、限制、克制、协同、境界差异和后文修正。同条件同结果的重复使用只增加出处与证据计数，不重复生成案例。

### 5.5 运行机制 `mechanism`

无专名社会规律必须表达参与者、目标、资源、信息差、权力与约束、常见策略、交互过程、成功和失败后果、适用范围、反例与失效条件。单一强证据可记录为已证实个案或局部机制；多案例一致后才归纳普遍规律。

### 5.6 推论 `inference`

系统允许综合多条正文事实推出小说未直接陈述的结论，但推论永久与事实分离。每条推论保存所用断言、逐步证据链、反例、未知项、置信度和失效条件。高置信推论也不能无证据升级为原著明示事实。

### 5.7 开放 Schema

第一版必须允许保存 `unclassified_claim` 和模型的原始结构提案。当前 Schema 无法表达时，内容进入扩展审查，不得因字段缺失而丢弃。

## 6. 复杂查询

机器查询和推理优先，人工百科其次。查询流程为：

```text
自然语言问题
-> 识别对象、关系、条件和时期
-> 结构化关系查询召回断言与案例
-> 语义检索补充相关证据
-> 按模式过滤
-> 推理器组合事实并搜索反例
-> 模型只依据查询结果组织中文答案
-> 返回引文、证据链、未知项与置信度
```

模型不得脱离检索结果凭记忆补充原著内容。

### 6.1 双查询模式

- **严格模式**：游戏开发默认使用。只返回已确认的最终设定；系统推论单独标识并附证据链；未确认候选和游戏补全不参与答案。
- **研究模式**：额外展示弱证据、冲突项、未确认候选、二手线索、系统推论和建议反查方向。

### 6.2 答案契约

复杂查询至少返回：

- `canonical_answer`：正文可直接支持的结论；
- `derived_inference`：跨证据推论；
- `reasoning_chain`：逐步使用的事实与条件；
- `counter_evidence`：反例、例外与冲突；
- `unknowns`：原著未说明部分；
- `confidence`：推论置信度；
- `citations`：逐项绑定的短引文和位置。

## 7. 自动化流水线

所有工作以可恢复任务队列执行：

```text
导入原文
-> 章节与场景切分
-> 全文与语义索引
-> 多路候选发现
-> 实体对齐与去重
-> 原文证据扩搜
-> 后文反证搜索
-> 原子化拆分
-> 自动裁决
-> 图谱递归扩张
-> 盲审与专项补扫
-> 发布知识库快照
```

每个任务记录输入哈希、依赖版本、模型版本、提示词版本、原始响应、解析状态、费用、耗时和重试状态。云端失败、非法结构或引文无法对齐时，不得产生半确认事实。

### 7.1 模型与工具路由

- 程序工具：切块、全文检索、位置对齐、重复检测、Schema 校验和引用校验；
- 中等成本模型：高召回开放发现、显式关系抽取、原子化与普通对象整理；
- 强模型：跨章节归纳、无名机制、角色可靠性、后文冲突和高影响裁决；
- 独立审计模型或独立提示路线：随机盲审，避免主管线共同偏差；
- 人工：少量重大争议。

任何具体云端供应商和模型名称都属于可替换配置，不写死在知识语义中。

### 7.2 失败恢复

- 非法模型结构进入重试或隔离队列，不写正式库；
- 引文无法逐字对齐时证据失效，相关断言降级；
- 新强冲突出现时撤销自动确认，重新进入裁决；
- 原文变化时通过块指纹局部失效和重算；
- 评分规则变化时利用保留的原始证据重算，无需重新调用全部模型；
- 发布快照记录原文指纹、Schema、模型配置和质量报告，以支持复现。

## 8. 覆盖审计与复刻级门槛

“复刻级”是经过审计的质量等级，不是无法证明的绝对零遗漏。

### 8.1 指标

- 正文解析覆盖率；
- 被独立发现路径处理的场景比例；
- 无候选、无纯剧情判定的长文本空白区比例；
- 二手候选的确认、否定和未确认比例；
- 随机盲审漏检率；
- 每轮新增对象、断言、机制和例外的收敛曲线；
- 最终设定的可定位正文证据完整率；
- 已确认断言的后文与反例检查率；
- 盲审发现的新 Schema 类型频率；
- 自动确认记录的独立抽样精确率；
- 每百万字、每确认事实和每任务类型的成本与耗时。

### 8.2 发布条件

首个复刻级知识快照至少满足：

- 正文解析和索引覆盖率为 100%；
- 已发布事实的正文证据完整率为 100%；
- 已确认事实的反证检查率为 100%；
- 连续多轮新增量达到校准后的收敛门槛；
- 随机盲审漏检率与自动确认抽样精确率达到校准阈值；
- `critical` 冲突已裁决或明确标为未知；
- 未确认候选不会泄漏到严格查询和游戏适配层。

具体数值阈值在阶段 0 通过高密度、低密度和跨时期修正三类样本校准，不在没有基准数据时拍定。

- `分支：六卷精编版/` 保持只读。
- `肉鸽设计-原始数据/` 只作为候选来源，未经任务明确要求不改写。
- 数据库、缓存、大型索引和批量生成报告默认不提交 Git。
- Schema、迁移、代码、提示词、来源元数据、人工裁决、小型测试夹具和经选择的报告样本进入版本管理。
- 现有 `docs/lore` 原则保留，并逐步转为知识引擎生成的审查视图与游戏适配登记，而不是并存一套长期手工真值。
- Godot `data/*.json` 只消费批准后的游戏适配产物，不直接读取研究库。

## 10. 分阶段交付

### 10.1 阶段 0：基准校准

选择三类固定样本：

1. 设定高密度片段；
2. 设定低密度、但包含社会机制的片段；
3. 前文说法被后文修正的跨章节片段。

建立小型人工金标准，比较切块、提示词、模型路由和检索策略，测量精确率、召回率、成本与耗时。样本只用于决定全书流水线，不替代全书处理。

### 10.2 阶段 1：可验证纵向闭环

打通真实原文上的完整流程：

```text
导入 -> 发现 -> 证据对齐 -> 反证 -> 裁决 -> SQLite
     -> 严格/研究查询 -> 质量与成本报告
```

最低验收问题：

- 丁等资质改变命运有哪些已证实方法？
- 小光蛊的原著能力、限制、实际案例和游戏改编分别是什么？
- 散修通常通过哪些机制获得资源，各自受什么约束？
- 《人祖传》中哪些内容只是世界内传说，哪些得到现实验证？

### 10.3 阶段 2：三路全书发现

汇总二手候选，对全文执行开放扫描与结构扫描，启动图谱递归扩张和后文反证任务，并按新增率动态调整专项扫描。

### 10.4 阶段 3：裁决与复刻级审计

批量聚合证据，自动确认低争议项，强模型处理高影响机制，只把重大未决争议交给用户。通过随机盲审与独立抽样复核后发布知识快照。

### 10.5 阶段 4：Roguelike 适配

适配器只查询严格模式，生成待审核的机制映射。每条适配必须记录：

- 引用的实体、断言、案例和机制 ID；
- 保留的能力、条件、代价、克制和社会意义；
- 因 Roguelike 形式而进行的抽象；
- 原著未说明而新增的游戏补全；
- 游戏平衡数值；
- 与现有机制规格的兼容性；
- 原著知识更新后的重新审查状态。

只有批准后的适配记录才可进入 Godot 运行时数据。

## 11. 测试策略

- **确定性测试**：切块、稳定 ID、字符位置、索引、迁移和去重。
- **Schema 测试**：非法模型输出不得进入正式库。
- **证据测试**：所有引文逐字对齐当前原文。
- **裁决测试**：角色谎言、后文修正、适用条件、反例与世界内传说。
- **查询测试**：严格模式不泄漏未确认候选、二手结论或游戏补全。
- **回归测试**：提示词、模型或评分变化不得在金标准上静默降级。
- **成本测试**：按字数、事实和任务类型记录云端成本。
- **游戏边界测试**：未经批准的知识记录不得进入 `data/`。

## 12. 首期明确不做

- 不立即对 700 万字执行全量昂贵模型调用；
- 不直接生成或改写 Godot 游戏内容；
- 不将二手资料自动确认为原著事实；
- 不估算原著未给出的概率、价格或战斗数值；
- 不把全文剧情整理成逐章事件账本；
- 不承诺数学意义的绝对零遗漏；
- 不引入图数据库、复杂 Web 管理后台或面向玩家的百科 UI；
- 不修改只读原文和用户当前 UI 工作。

## 13. 首期成功定义

阶段 0 与阶段 1 完成时，应存在一个可复现的真实原文闭环，而不是概念演示：

- 三类基准样本和人工金标准已固定；
- SQLite Schema、迁移与任务缓存可用；
- 至少三条独立候选发现路径能够共享候选池；
- 引文可逐字对齐，后文反证可执行；
- 自动裁决能够正确降级不确定项；
- 严格与研究模式能够回答最低验收问题；
- 质量、成本、漏检和争议报告可生成；
- 基准结果足以决定全书扫描的模型路由和验收阈值；
- 原著知识层与游戏适配层之间有自动化边界测试。

达到以上条件并审阅实测结果后，才制定并执行阶段 2 至阶段 3 的全书处理计划。
