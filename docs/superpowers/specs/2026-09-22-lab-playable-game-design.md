# 《问真》Web 可玩游戏本体交付规格

日期：2026-09-22。L0 最新指令：开发到 `lab.html`，以一个可玩的游戏本体为验收，不继续停在原型阶段；不做 Godot。

状态：交付目标已获 L0 授权；本文是基于现有规则的工程收敛规格，不新增玩法、数值或正式单局时长裁决。关联计划：`../plans/2026-09-22-lab-playable-game.md`。

## 1. 玩家最终拿到什么

一个可以直接打开、开始游戏、持续游玩、关闭后继续、完成胜负结算并重新开始的 Web 游戏。入口固定为 `game/wenzhen-web-lab/lab.html`；交付包中仍为 `game/wenzhen-web-lab/lab.html`，附可直接点击的启动说明。

完整循环：大厅 → 新局/继续 → 节点选择 → 战斗或节点事件 → 实际奖励入袋 → 整备（购买、卖出、炼化、合炼、杀招配置、修为突破）→ 下一节点 → 第五层主胜利结算或死亡结算 → 大厅/再来一局。

第一版沿用当前五段图结构和既有难度数据，不发明新地图或扩内容。普通难度当前有每段 10 个准备深度和 1 个层主，一条完整路线为 55 个节点；候选图的 155 个节点不能被当成玩家实际游玩 155 节点。五段终点不是修为五转要求，不冻结最终产品 Run 时长。

## 2. 产品完成标准

| ID | 玩家可观察的结果 | 必要证据 |
|---|---|---|
| G01 | 普通玩家打开入口即可知道目标和下一步，无需开发者解释或控制台 | 全新浏览器配置下的启动与首战录屏/截图序列 |
| G02 | 新局、继续、刷新恢复、取消重开、确认重开均可靠 | 战斗/待领奖/整备三个中断点，恢复后状态与下一次结果一致 |
| G03 | 只能走合法后继；换页不逃掉当前遭遇，不跳关、不伪胜 | 实际页面操作和节点/事件日志对照 |
| G04 | 战斗的意图、观察、蛊、杀招、消耗、反制、敌人回合和胜负都真实生效 | 观察后改变行为与相同局面直接行动的对照轨迹；预览与结算相符 |
| G05 | 战利品、商店扣款、购买入袋、材料与炼制、突破处于同一局状态 | 至少一条正常开局的完整资源账本，不改 `state`、不额外注资 |
| G06 | 获得/失去组件影响杀招可用性，组合同回合占用、封印和成本可信 | 实际界面组装/配置、使用、卖出/炼耗组件后的回归 |
| G07 | 存在可通过正常操作获胜的路线，也存在可解释的失败和重新尝试 | 普通难度两种不同构筑选择的完整获胜轨迹；自然失败或合法主动冒险的死亡轨迹 |
| G08 | 所有可见控件有响应，禁用说明缺少什么；玩家页无覆盖表、测试演武入口和虚假可用功能 | 大厅、节点、战斗、奖励、整备、结局六类页面逐页检查 |
| G09 | 同种子同操作可复现；不同种子的地图/货架/掉落不被入口固定种子抹平 | 固定 101–110 种子集的结构与资源轨迹摘要；不要求每个随机字段都不同 |
| G10 | 脱离开发仓库后仍能游玩，核心资源不缺失；存储失败有明确提示 | 解压到空目录、离线启动、完整冒烟和读档恢复 |

G07 的“两种构筑”是交付覆盖目标，不是强制平衡各流派；不能为了达标偷偷改价格、伤害、奖励或突破成本。若现有数值使其不可达，提交具体轨迹和应用点给 L1/L0，未闭合前交付状态为 BLOCKED，不能改叫 ACCEPTED_WITH_GAPS。

## 3. 保留的现有实现

- `js/main.js`：当前 `state` / `act` 命令入口与主循环，直接修接缝，不整体重写。
- `js/run_flow.js`：节点图、阶段显示、突破条件；`js/run_rules.js`：恢复、奖励、确定性计算。
- `js/gu_rules.js`、`shop_rules.js`、`loot_rules.js`、`node_action_rules.js`：复用已有规则。
- `js/journey.js`、`battle.js`、`alchemy.js`、`killmove.js`、`css/lab.css`：现有玩家界面与视觉方向。
- `js/combat_core.js` 是现有 `MvpLogic` 的包装，不能仅凭文件注释认定它已成为全部战斗的唯一结算入口；需要逐调用点验证。
- `game/data/*.json` 仍为已有数据 Owner；Web 经 `tools/build_data.mjs` 消费，不改 Godot 代码或启动 Godot。

## 4. 已确认的交付接缝

取证基于 2026-09-22 的脏工作树；另有执行者在开发，实施前必须重新冻结该批文件指纹。

1. `main.js::fresh/startRun/restartRun` 与 `journey.js::renderHall` 直接重建状态，当前没有浏览器存储、刷新恢复或重开确认。
2. `main.js::openBattleOutcome/rollVictoryLoot/buyOffer/forge/breakthrough` 已有实际业务动作，不应以“没有购买/掉落引擎”为由重写。
3. `lab.html` 的覆盖页和 `battle.js` 无战斗时的演武列表属于开发入口。玩家导航还可能从处理中页面离开，须检查继续入口及防绕过。
4. `main.js::endJourney` 与 `renderEnding` 已有结局页面；问题是终局状态、恢复和再开局的完整性，不能写成“没有任何胜利页面”。
5. `tools/autoplay.mjs` 仍操作短剧本 `index.html`；不能代表 `lab.html` 五段游戏验收。
6. `tools/check_progression_loop.mjs` 有 `stones=10000`、手写突破配置与直接加元石，且使用 `MvpLogic.createRun/applyForge`。只能作局部测试，不能宣称正常玩家闭环已经完成。
7. `READY` 现有 14 类持有蛊，含高转内容。首版先冻结实际开局快照；不得由 Worker 擅自删蛊、降低奖励或更换开局配置来制造通过。开局配置若需要产品调整，提交单独决策项。
8. 资源路径存在 `assets/...` 与 `../assets/...` 混用；`_link_assets.mjs` 只复制少量 MVP 资源，不能直接当完整发行打包器。

## 5. 实施边界与取舍

采用“把现有 lab 主链收敛成可交付游戏”：先可启动并续玩，再保证命令与结算一致，再完成正常游玩和发行验收。新开前端/引擎需要重做当前规则；仅给短剧本换标题又无法覆盖长线成长，均不采用。

允许新增的工程代码只针对已确认缺口：浏览器存档适配、lab DOM 自动走盘、发行资源清单与验收报告。它们不是新的 Rank、经济、战斗或杀招引擎。

玩家模式隐藏调试入口，开发测试可保留；UI 沿用现有美术、音效和组件，不进行新美术方向设计。当前声明式杀招保留，组件替换后自动推导效果仍不在授权范围。

以下仍未裁决：正式单局是否必须 R1→R5、黄金/紫晶倍率、高转经济倍数、跨转固定倍率、五转出现率、新的跨局继承。继续保持未决，不塞进本计划。

## 6. 状态与交付纪律

每批只能标 READY_FOR_REVIEW / FIX_REQUIRED / PASS / BLOCKED。最终发布验收只有 PASS 或 BLOCKED；核心链路缺口不得列为“已接受的后续任务”。

自动化只验证游戏状态与行为；玩家能否理解目标、看清风险、看懂失败原因还需真实浏览器巡检。所有成功结论附真实输出、日志和截图路径。

本规格不要求新的服务端、账号、云存档、联网、订阅、部署或永久成长系统。
