## 1. 本件的定位与纪律

按 L0 指令，本阶段**禁止开发**，先出需求重构计划。因此本件：

- **不做产品决策**。核心体验、内容上限、视觉方向、载体选型全部标为「待 L0 裁」，只给候选与证据。
- **不发明设计**。凡是已有权威件写过的，一律引用而不重写。
- **每个结论可复核**。数字附实测口径，判断附反例。

## 2. 失败归因：L0 的六条结论，逐条对仓库取证

| L0 结论 | 仓库实测证据 |
|---|---|
| **核心玩法不足** | `gu.json` 共 **802** 只蛊，只有 **61** 只（7.6%）有手写 `v1_effect`；其余 **741** 只走 6 行 role 兜底表，且该表是「每转 +1」的线性律（attack 2→6），五转只有一转的 3 倍。`v1_battle.json` 全部杀招 **26** 条。构筑空间在数据上很宽，在**可玩差异**上极窄。 |
| **UI / 视觉方向未经验证** | 三代视觉同时存在于仓库：① Godot 侧纸墨 token（`gu_style.gd`）；② Web 原型原本的深色 UI；③ 我刚提交的纸墨改造。`wenzhen-visual-style` 技能自称「唯一权威规范」，但**没有任何一份文档记录它经过 L0 审美验收**——权威是自称的。 |
| **战斗缺少策略深度** | 数据写了、校验器写了、运行时没接：`phases`（多阶段 AI）在 5 个 Boss 上有数据且 `enemy_catalog.gd` 有严格 schema 校验，但 `until_hp_ratio` 在 `scripts/` 下**只出现在那个校验文件里**——运行时零消费。后果：这 5 个 Boss 打起来和单意图杂兵完全一样。同类还有 `sparked`（唯一出现处是数据声明，无任何语义定义）与 `essence_burn`（零命中）。 |
| **资源系统没有形成闭环** | `true_qi_cost` 只在 **3** 只蛊上有键；`essence_cost` 只有 **16** 只（占 2%）；按 `v1_battle_resolver.gd:224` 的兜底口径实算，**794 / 802 只（99%）的战斗耗真元都是 1**——来源是那行字面量缺省值，不是设计。真元因此不是一个经济量，是一个常数。 |
| **大量功能先于需求实现** | 手写 **134** 个 GDScript / **36,589** 行；测试 **222** 文件 / **36,591** 行（测试与代码 1:1）；**66** 个场景；**30** 张数据表；**13** 份契约文档；**468** 条炼蛊配方；**12** 个事件。而 2026-09-17 的 M0 契约锁死的上限是：**6 只蛊、3 种杂兵、1 个 Boss、4 场战斗**。规模超出契约两个数量级。 |
| **AI 执行容易偏离设计意图** | 偏离不是「做错了」，是「做了但没接线」。本轮新加的 data→runtime 契约测试一上线就抓到成片的「数据声明了、运行时无消费点」（`phases` / `sparked` / `essence_burn`）。这类缺陷不会被单元测试发现，因为它不报错，只是**静默不生效**。 |

## 3. 最关键的一条发现（本件的核心判断）

**核心体验不是没被定义，是定义完没有被执行。**

`game/docs/superpowers/specs/2026-09-17-m0-core-loop-contract.md`（三天前）已经写对了：

```text
观察敌意 → 分配真元 → 使用蛊虫 → 承担结果 → 获得奖励 → 改变 Build → 再战
```

并且它做对了三件难得的事：

1. **锁死了内容上限**（1 角色 / 6 蛊 / 3 杂兵 / 1 Boss / 1 资源 / 3 选 1 / 4 战）；
2. **写了单一放行条件**（五项，其中第 2 项要求「不同随机奖励让两局出现不同**战斗策略**，而非只改变数值文本」）；
3. **自己承认了缺口**——原文最后一段：

   > 「M0 工程闭环通过，允许进入下一阶段的内容设计；**『是否足够好玩』仍需真人试玩作为体验结论，不得用自动化通过替代**。」

之后三天发生的事：没有去补那场真人试玩，而是加了世界模型、三轴数值体系、P1/P2/P3 数值管线、两条 Web 原型、802 只蛊、468 条配方。

**所以 V2 的第一性问题不是「核心体验是什么」，而是「为什么一份写对了的 MVP 契约拦不住项目膨胀」。** 本计划后半部分的重点在这里。

一个佐证：M0 契约的验收证据全是 `test_m0_core_loop.gd`、`test_wenzhen_ui_flow.gd` 这类**自动化**证据，而它自己写明这些「不能替代真实玩家是否会因此采取不同策略的行为观察」。**唯一没被满足的放行条件，正是唯一没法用测试满足的那条。**

## 4. 核心体验（候选，**待 L0 裁决**）

**不重新发明。** M0 契约的核心循环与五项核心契约（每回合有真实判断 / 敌人可预测可针对 / 奖励推动下一次选择 / 随机只负责制造问题 / 循环短且可重复）已经足够准确，本件建议**整段继承**。

V2 需要 L0 拍板的只有一件事：**要不要给这条循环加一句「问真之所以是问真」的主张。**

本件提出一个**候选**（不是决定）：

> **在有限资源与不对称信息下，靠读懂对手、并付出真实代价，取巧取胜。**

支持它的证据（均来自本仓数据设计，不是我编的）：

- 战斗数据里有 `clues`（线索）与 `reactions`（反击）两套机制，设计意图明显是「先观察、再决策」——`action_preview_service.gd` 里甚至有 `counter_revealed` / `counter_hidden` 与预警文案；
- M0 契约第 2 条已经要求「敌人行动可理解、可预测、可针对」，第 1 条要求「观察敌人下一步行动」；
- 原著侧（据本仓 wiki 与既有裁定）蛊师之间的胜负长期由**信息差与代价承受力**决定，而非等级压制。

**反面意见（必须一并呈给 L0）**：这条候选与 M0 循环「是同一件事的两种说法」，加它可能只是修辞。若 L0 认为 M0 循环本身已经表达了问真，则第 4 节可以整节砍掉，直接进第 5 节。

**明确上抛**：这条主张涉及「我们到底想做什么」，属 L0 权域，L2 与 L1 均不得代决。

## 5. 最小可玩闭环（沿用 M0，不新造）

三段循环，全部照抄 M0 契约：

| 层级 | 循环 | M0 给的时长目标 |
|---|---|---|
| 一场战斗 | 看敌意 → 用蛊并消耗真元 → 敌人行动 → 回收部分真元 → 击败 | 30 秒 – 2 分钟 |
| 一局 | 4 场战斗（杂兵 → 杂兵 → 精英 → Boss），每场后三选一 | 5 – 10 分钟 |
| 一个 Build | 拿奖励 → 改蛊囊 → 下一场打法不同 | 跨局 |

**MVP 的验收 = M0 五项放行条件 + 补上它自己承认的那条缺口（真人试玩）。**

建议 V2 把这条缺口变成**硬门禁**而不是注释，例如：不完成 N 人试玩并记录「第二局是否用了不同策略」，不得进入 P1。

## 6. 第一版范围（V1）

**建议直接沿用 M0 锁死的数字**（1 角色 / 6 蛊 / 3 杂兵 / 1 Boss / 1 资源 / 3 选 1 / 4 战）。
理由：那组数字是唯一一份经过论证的上限，且已经跑通过工程闭环——缩小它没必要，放大它正是第一轮的病因。

若要调整，需 L0 明确指定，并说明为什么 M0 的数字不够。

**非目标（V1 明确不做）**：完整世界观、境界系统、完整炼蛊与养蛊、NPC 好感、剧情树、局外科技树与永久成长、复杂地图、装备系统、存档成长、大量属性——**这一段同样照抄 M0 契约原文，不新增**。

## 7. 必须删除 / 冻结的内容

第一轮的症状是「功能先于需求」。**收缩必须有具体对象，否则就是口号。** 以下逐条给出实测规模与建议处置（处置需 L0 授权，涉及既有资产）：

| 对象 | 实测 | 建议处置 | 依据 |
|---|---|---|---|
| `gu.json` 的 802 只蛊 | 仅 61 只有手写效果；741 只走兜底 | **冻结**：V1 只用「原文站得住 + 有手写效果」的子集；其余保留在库但不进玩法池 | 占多数的是机器拼名与无着落条目；上一轮魂道审计已实测 40 只魂道蛊仅 4 只原文站得住 |
| 468 条炼蛊配方 | 151 条为贵金属/高阶铺量 | **冻结**：V1 只放行与 V1 蛊集闭包相关的配方 | 配方数量是内容规模，不是核心体验 |
| 66 个 Godot 场景 | 含调试台、旧屏 | **归档**：V1 只保留闭环路径上的屏 | M0 已示范「隔离垂直切片」的做法 |
| `phases` / `sparked` / `essence_burn` 等未消费字段 | 已接线 `phases`+`essence_burn`；`sparked` 仍无语义 | **冻结语义**：`sparked` 无定义就保持不实现（已登记豁免） | 「写不进脚本的规则不许存在」 |
| 三代并存的视觉方案 | 纸墨 token / 深色 UI / 我刚提交的改造 | **收敛为一条**——方向待 L0 定（见 §9） | 视觉方向未经验证正是失败项之一 |
| 13 份契约文档中已作废的部分 | `agent-ownership-contract` 等 | **归档**：不再作为执行契约 | 已有 `CONSTRAINTS-V2` 明确作废 |

**不建议删除已有代码。** 处置以「冻结 / 归档」为主：删代码风险高、收益低，而**把入口关掉**已经能达到收缩目的。

## 8. 后续开发路线（P0 → P3）

与 L0 给的优先级一致，此处只补「每阶段的通过条件」：

| 阶段 | 内容 | 通过条件 |
|---|---|---|
| **P0 核心玩法验证** | 蛊虫构筑 / 战斗决策 / 资源取舍 | M0 五项放行 + **真人试玩**记录（第二局策略是否不同） |
| **P1 成长循环** | 炼蛊 / 养蛊 / 交易 / 传承 | 成长必须改变 P0 的决策空间，而非只加数值 |
| **P2 世界扩展** | 地图 / NPC / 剧情 / 美术 | 视觉方向已由 L0 确认；世界内容服务 P0 的信息差与代价 |
| **P3 外围系统** | 设置 / 存档 / 成就 / 优化 | — |

**跨阶段硬约束（本件建议写入 `game/AGENTS.md`）**：任何阶段的规模不得超过该阶段契约锁定的上限；**未通过前一阶段的放行条件，不得开启下一阶段**——这正是第一轮失守的地方。

## 9. 开工前必须由 L0 裁决的五件事

**这五件未定，V2 无法进入实施。** L2 不代决：

1. **载体**：V2 建在 Godot 还是 Web？
   现状冲突：L1 已裁（`RUL-2026-09-19-010`）「Godot = Canonical，Web = Disposable Prototype，双线手抄 REJECT」，且「弃 Godot 需通过 7 项 Production-Equivalent Bake-off」；而 L0 指令是「别跑 Godot 了，做 Web」。**该裁决的前提已被改变，需重裁或明确作废。**
2. **视觉方向**：L0 指令为「禁止直接继承旧水墨方案，重新研究原著提出方案」。
   现状冲突：`wenzhen-visual-style` 技能自称「唯一权威规范」，而我刚按它提交了 `6b855b9`（纸墨改造）。**该技能是否降级为历史参考？`6b855b9` 是否回退？** 另需注意：该技能的硬流程要求「线框稿先行 + 用户批准」，而它从未走过这一步。
3. **核心体验主张**：§4 那条候选是否成立？（或直接继承 M0 循环，砍掉 §4）
4. **V1 内容上限**：是否原样沿用 M0 的 6 蛊 / 3 杂兵 / 1 Boss / 4 战？
5. **收缩授权**：§7 的冻结 / 归档清单是否授权执行？
