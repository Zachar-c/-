# 核心玩法原子原型 · 交接（2026-09-19）

> 独立于 `wenzhen-web/`（叙事原型）与 Godot 线的第三个实验：**同样的核心玩法元素，用 Web 做一遍**，
> 用来回答一个问题——**质量与效率是否已足以让这个项目舍弃 Godot、全转 Web？**
>
> 与叙事原型的分工：`wenzhen-web/` 验的是"电影化叙事 + AI 生产循环"；本目录验的是"系统与战斗"。
>
> **定位（2026-09-19 用户确认）**：这不只是技术试验，还是**功能验收台**——把已实现与新开发的功能
> 摆在网页上，让开发者当场确认没问题。用户认为这比 Godot 项目里的调试台更进一步。

---

## 一、一句话现状

**单页四个面板：炼蛊（真实配方 + 失败代价）→ 杀招（真实配方组装入槽）→ 战斗（线索与反击的隐藏/揭示、
直接攻击被反击吞掉、多阶段 AI 与冷却门禁、焚元意图、真元回复、护体结算）→ 覆盖（本页验了什么、没验什么）。**
跑在 Godot 项目的真实数据表上，复用 Godot 项目的美术与字体。

## 二、怎么跑

**直接双击 `index.html` 就能用**（2026-09-19 修正）。本目录**不用 ES module**，脚本按顺序普通加载；
美术与字体走相对路径 `../../assets/wenzhen/...`，所以 `file://` 与 `http://` 两种方式都能跑。

若仍要用本地服务（例如需要 `fetch` 或跨目录调试）：

```powershell
cd <repo>/game
"C:\Users\90877\.workbuddy\binaries\python\versions\3.13.12\python.exe" -m http.server 4177 --bind 127.0.0.1
# 打开 http://127.0.0.1:4177/wenzhen-web-lab/index.html
```

`?silent=1` 关音频（无头验证用）。

**为什么不用 ES module**：`file://` 下 module 脚本会被 CORS 直接拦死（`Access to script ... from origin 'null' has been blocked`），
表现为**按钮全部无响应**——脚本从未执行。叙事原型 `wenzhen-web/` 用的是 module，因此它必须起服务；
本原型选了普通脚本，换来"双击即开"。代价是没有 `import` 的类型边界，靠加载顺序（见 `index.html` 注释）维持依赖。

**故障识别（2026-09-19 加）**：脚本没执行时，页面会出现红框「原型脚本没有执行」。
看不到这个框却仍然点不动，说明不是脚本问题而是看错了副本。
另有两条旧版本特征可肉眼分辨：HUD 数字停在 `20/20 · 3 · 3 · 12`（静态默认值），背景全黑（旧版绝对路径 `/assets/` 404）。
遇到就 **Ctrl+F5 硬刷新**；仍如此说明打开的不是本目录这份文件。

## 二·五、视觉层（2026-09-20 改造：改用项目权威规范）

**改前**：本页是一套**深色 UI**（`--bg:#0a0b0d`、浅色文字、金/翡翠强调），
与项目唯一权威视觉规范无关——即 `game/.agents/skills/wenzhen-visual-style/`，
其基线是 `assets/base_ref.png`（1405×790），token 真源是 `scripts/presentation/gu_style.gd`。

**改后**：`css/lab.css` 变成那套 token 的 CSS 镜像（注释里逐条标了对应的 Godot token 名）。
关键对照：

| 概念 | Godot token | 本页 CSS |
|---|---|---|
| 纸底 / 卡面 | `PAPER_BG` / 卡面浅纸 | `--paper` `#ece9df` / `--paper-card` `#f6f3e9` |
| 墨（主/次/注） | `INK_PRIMARY`/`INK_SOFT`/`NOTE_TEXT` | `--ink` `#171814` / `--ink-soft` `#686960` / `--ink-note` `#607060` |
| 朱砂 / 印章 / 红线 | `CINNABAR`/`SEAL_CINNABAR`/`REDLINE` | `--cinnabar` `#9c332d` / `--seal` `#8c5850` / `--redline` `#82463e` |
| 语义四色 | `STATUS_CONTRACT`/`MUTATE`/`CURSE`/`JADE` | `--contract` / `--mutate` / `--curse` / `--jade` |
| 按钮 | `BTN_OUTLINE_BLUE` | `--btn-outline` `#3880b8`（透明底 + 1px 描边 + hover 转朱砂、无阴影） |

**三条落地纪律**：
1. 背景必须是「纸底 + 网点」两层：`#bg` 铺 `assets/wenzhen/hall/hall_dots.png`（1280×720 网点场）。
2. **美术资产本身就画在纸底上**（道徽、敌人立绘都是），所以一律用 `mix-blend-mode: multiply`
   让它们的纸融进界面纸，而不是当矩形贴片。**不要**给它们套深色 UI 时期的
   `filter: saturate(.6) brightness(.75)`——那会把画作压成灰片。
3. 立绘源是**方图**，画框用 `aspect-ratio: 1/1` + `object-fit: cover`。
   用 `3/4 + contain` 会在上下留两道底色空带，看着像没加载完。

**验证方式**（本页命脉：AI 要能自己看图）：
`node ../wenzhen-web/tools/drive.mjs "<file:// 路径>?silent=1" "<计划>" "1280,720"`，
计划里用 `eval:document.querySelector('[data-tab=battle]').click()` 之类做真实点击，
截图落在 `.preview/*_render.png`。**交付前必须真看图**，不能只凭 `dataset.ready===1` 宣布完成。

## 三、真实数据 vs 原型设定

**真实（来自 Godot 数据表，`tools/build_data.mjs` 抽取）**

| 内容 | 来源 |
|---|---|
| 10 只蛊：名称/转数/稀有度/流派/价值/效果 | `world-model/data/gu.json`（802 实体中的子集） |
| 6 条配方：材料、元石成本、出处原文行号 | `data/refinement_recipes.json`（468 条中筛出） |
| 3 个杀招：配方、真元/念头消耗、效果 | `data/v1_battle.json` → `kill_moves`（26 条中筛出） |
| 6 个敌人：中文名、气血、意图与伤害 | `data/enemies.json` + `data/names.json`（`names.enemies`） |
| 敌人线索与反击：`clues`、`reactions`（`trigger`/`window`/`counter_status`/`label`） | `data/enemies.json` |
| 多阶段 AI：`phases[].until_hp_ratio` / `intents` / `reactions` | `data/enemies.json`（32 个敌人里 5 个带 `phases`） |
| 意图冷却语义 | `data/enemies.json` → `miasma_vein_lord._phases_note`（数据自带规则说明） |
| 真元上限、每回合回复、资质系数 | `data/v1_battle.json` → `stage_base` / `regen_pct` / `aptitude_mult` |
| 反击判定规则（哪种反击生效、何时被抑制） | `scripts/domain/action_preview_service.gd:325-347` `_live_counter_labels` |

**规则直译（不是仿写）**：`js/rules.js` 把 `_live_counter_labels` 的判定照搬——`trigger=direct_strike`、
`window=before_damage`，且 `counter_status=bound` 遇 `enemy_bound`、`guarded` 遇 `guarded` 时该反击失效。
被吞掉后敌方转入对应状态，预警随之消失；此后直接攻击可以打进去。

**多阶段 AI（2026-09-19 新增，本页是首个实现）**：分段依据在数据里早就写好了，只是**没有运行时**：

- 当前阶段 = 数据顺序中**最后一个 `until_hp_ratio ≥ 当前血量比`** 的阶段（阈值按数据顺序严格递减）。
- 每阶段的意图表与反击表都可以不同；阶段切换时战报打「敌方转入第 N 阶段」。
- **冷却门禁**照抄 `_phases_note` 原文：`cooldown:n` 表示第 T 回合发出后，**最早 T+n+1 回合**才能再选；
  当前阶段所有意图都在冷却时，该回合敌方**什么都不做**（`cooldown_wait`），战报记「蓄势不动」。
- 意图为公开信息（每回合显示下一手），配合「观察」揭示的线索与反击，构成"读招—决定是否直接攻击"的循环。
- **原型设定**：数据没写多个意图之间的优先级，本页取**数据顺序**；Godot 侧无实现可对照。

**原型设定（不是原著也不是现有平衡，写在这里备查）**

- 合炼成算固定七成；失败时本次投入中最低转的那只消亡（依据原文个案：合炼失败，小光蛊消亡）。
- 开局持有 8 只蛊、3 颗元石、3 个念头、**24 气血**；真元上限 = `stage_base.one × aptitude_mult.bing` = 20（丙等一转）。
  （气血原设 12，2026-09-19 提到 24：12 点气血打不过 20 血的 Boss，会在看到多阶段之前就死，AI 验不出来。）
- 胜利奖励元石 +2（原型设定，非现有经济）。
- 护体只抵挡当前回合的敌方反击，回合结束清零。
- 「观察」= 花 1 念头 + 1 回合，揭示该敌人的全部线索与反击（Godot 侧 `counter_revealed` 的触发条件未移植）。
- 「直接攻击」口径 = 效果 `kind` 为 `strike` 的杀招；Godot 结算器只检查基本拳脚/荆棘鞭击那类路径，本页以 strike 近似。

## 五、发现的数据问题（本页顺手报出来，Godot 侧可核）

1. **`counter_status="sparked"` 无规则实现**：`data/enemies.json:153`（雷冠头狼「雷甲反噬」）声明了该状态，
   但 `scripts/` 与 `docs/` 里零命中；`_live_counter_labels` 只枚举 `bound`/`guarded`，
   因此这条反击在 Godot 侧永远算「生效」、且没有任何东西能解除它。
   数据分布：`bound` 11 条、`guarded` 16 条、`sparked` 1 条。
   本页已从反击列表剔除，并记入覆盖页「未覆盖」。`tools/build_data.mjs` 每次运行都会打印这类漂移。
2. **线索没有中文名**：`data/names.json` 没有 `clues` 分区，敌人线索只有 id（`stone_dust`、`steady_stance` 等）。
   本页照原样显示 id，不自行译名。（注意 `names.reactions` 是社交态文案如「对方保持谨慎」，与战斗反击无关，勿混用。）
3. **多阶段 AI 与焚元意图：数据写了，Godot 运行时没实现**（本页就是为验它才做的）。
   全仓检索结果：
   - `phases` 只出现在两处 **schema 校验**里——`scripts/domain/enemy_catalog.gd:170-200`（`_validate_phases`，校验
     `until_hp_ratio` 落在 `(0,1]` 且严格递减、`intents` 非空、`cooldown` 合法）与
     `scripts/domain/content_catalog.gd:1432`（DDA boss-local 校验意图是否在某个阶段的池子里）。
   - `until_hp_ratio` 同样只在 `enemy_catalog.gd:174-199` 出现，**没有任何代码按血量比选阶段**。
   - `essence_burn` 在 `scripts/` 下**零命中**（`intent` 里也没有它的读取位置：
     `battle_command_facade.gd:171-179` 复制的是 `label`/`speed`/`seal_turns`/`soul_drain`/`life_cost`/`counter_tag`，没有 `essence_burn`）。
   - 结论：32 个敌人里 5 个带 `phases`（`miasma_vein_lord`、`thunder_crown_sovereign`、`blood_vein_bishop`、
     `clan_patriarch`、`blue_fur_jiangshi`），在 Godot 侧**打起来和单意图的杂兵一样**。
     这大概率就是"AI 看起来很呆"的根因——**不是 AI 逻辑要重新调研，是这套逻辑一直没接线**。
   - 语义说明只在 `miasma_vein_lord._phases_note` 一条字段里（其余 4 个 Boss 没写），本页照它实现。

## 六、未验证（明确留待）

- 真机（非无头）字体渲染与性能；本原型无动画/粒子压力测试。
- 音频听感：`js/audio.js` 是程序合成，无头下静音，只确认代码路径不报错。
- 确定性、存档、事件日志、撤销：**全部没有**。Godot 侧有的这套工程保障，本原型一行都没实现。
- 移动端/小视口适配。
- **立绘借用**：`blood_vein_bishop`（血络主教）没有专属立绘，借用 `enemy_bat.png`；覆盖页已标为近似。
- **多阶段 AI 只验了 2 个 Boss**：另 3 个带 `phases` 的数据（`miasma_vein_lord`、`clan_patriarch`、`blue_fur_jiangshi`）没进本原型，
  因此没验证"3 阶段以上""阶段内意图更多"的情形；阶段内**多意图的优先级**也无从对照（数据未写明）。
- **阶段切换没有动画**：只在战报里打一行字，视觉上没有"变形态"的反馈。

## 七、与 Godot 的规模对照（同口径实测，2026-09-19）

| 项 | Godot 线 | 本原型 |
|---|---:|---:|
| 手写代码 | 134 个 GDScript / 36,363 行 + 28 场景 | 10 个文件 / 1,041 行（另有 686 行 `js/data.js` 是生成的） |
| 测试 | 232 个脚本 / 36,088 行 | 0（靠无头驱动 + 断言 + 截图） |
| 数据表 | 30 个 JSON / 27,283 行 | 0（直接读 Godot 的表） |
| 契约文档 | 13 份 | 0 |
| 单个战斗结算模块 | `v1_battle_resolver.gd` 1,099 行 | `js/battle.js` + `js/rules.js` |
| 单个炼蛊规则模块 | `refine_command_rules.gd` 990 行 | `js/alchemy.js` |

**口径警告**：这不是同类比较。Godot 侧是**生产级**实现——确定性种子、不可变事件日志、存档迁移、契约与门禁、
1556 个测试用例；本原型是一次性的可视玩具，规则被大幅简化（覆盖页里逐条列了没做什么）。
**行数差距衡量的是"从想法到看得见"的距离，不是质量差距。**
真正的对照点只有两条：**① 见到第一个可玩画面的时间；② 改一次视觉/数值后重新看到结果的时间。**

## 八、下一步（需拍板）

**这一轮"AI 很呆"的结论先行**：不用去调研开源 AI 逻辑树。这套逻辑（阶段 / 冷却 / 焚元）**在本仓自己的数据里已经设计完了**
（`enemy_catalog.gd` 甚至写了严格的 schema 校验），缺的只是运行时那几十行选招代码。本页用 `js/rules.js` 把它实现了一遍作为参照。
所以真正的问题不是"移植谁的 AI"，而是**要不要把 Godot 的 `v1_battle_resolver.gd` 接上 `phases`**——数据与校验都已就位。

三选一：

1. **继续加深（决定性实验）**：把 `reactions` 之外的规则也搬上来（多敌遭遇、念头/魂魄、剑道刻痕、掉落与地图节点），
   看 Web 在规则复杂后是否还保持这个改写速度。这是决定"能不能全转 Web"的关键实验。
2. **扩成正式验收台**：把 Godot 侧更多已实现系统（地图节点、掉落、商店、社交）按同样方式搬上页面，每个面板自带"已覆盖/未覆盖"清单。
3. **冻结**：认定 Web 只适合做原型/导演工具，正式交付仍回 Godot。

**旁支（成本很低，可单独做）**：把 `phases` 的选招逻辑补进 Godot 的 `v1_battle_resolver.gd`。
参照实现就是 `js/rules.js` 里的 `activePhase` / `selectIntent` / `intentReady` 三个纯函数（共约 30 行，无副作用、可确定性测试）。
要先补的缺口是 `essence_burn` 的效果结算（`battle_command_facade.gd:171-179` 目前在丢弃这个字段）与 `_phases_note` 在多意图优先级上的空白。

## 九、纪律

- 不碰 Godot 线（`scripts/`、`scenes/`、`data/`、`world-model/` 只读）。
- 不做预抽象：没有 Manager / EventBus / 状态管理 / 构建步骤。
- 判定与表现分离：判定写在 `js/rules.js`，面板只显示与派发。
- 数据只有一条来源：`tools/build_data.mjs`，手改 `js/data.js` 会在下次生成时被覆盖；
  它同时充当漂移检测入口（数据写了但规则没实现的，直接打印）。
