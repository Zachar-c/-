## 2. 更正一：80 不是「构建脚本中的孤立字面量」

它是**游戏侧文档化的「出身气血」**，三处互相印证：

**(a) 游戏本体的开局状态定义（GDScript，可玩路径）**

```gdscript
# 2026-08-31 数值重做：出身丙等满真元 20（10×丙等2×一转1）、80 气血、
# 60 年寿元、魂魄底蕴 1（每回合 2 次行动，底蕴分档抬升）。
var health: int = 80
var max_health: int = 80
```

同文件存档序列化处另有两处裸字面量：`"health": 80, "max_health": 80`。

**(b) 战斗数据契约文档**

```jsonc
"hp": 80, "max_hp": 80,        // 出身气血（cultivator.health，随重做 80）
```

**(c) 只读数值对账 C9 条目（本会话早前由我独立认定的分叉）**

> 「玩家气血 80 vs 100，且 80 是硬编码……**"玩家到底 80 还是 100"没有单一来源**」

**结论**：80 同时存在于**游戏本体**（玩家实际开局就是 80 血）、**旧构建脚本**、**数据契约文档**。
它不是「只藏在构建脚本里」，而是「**游戏本体正在跑的值**」。

你要的「不许藏裸字面量」这一点依然成立，而且比原判断更严重：80 是**活的**裸字面量，在游戏本体里有定义 + 序列化共 3 处。

## 3. 更正二：我此前给你的一条陈述是错的

我在 RR（Q11）里写过：「另外气血每回合还有 `+2`、上限 `+6` 的增长规则」。
**这句是错的**——`+2/回合（上限 +6）` 是**敌人在单场战斗内的回合膨胀**，不是玩家气血成长。

真实口径（数值键，构建产物内可直接读取）：

```json
"run.turn_scaling": { "hp_add_per_turn": 2, "damage_add_per_turn": 1,
                      "hp_cap_bonus": 6, "damage_cap_bonus": 2 }
```

应用处注释：`按 turn_scaling 逐档叠加 HP/伤害并受 cap 限制；Boss 再乘 boss_layer_mult`
——该函数缩放的是**敌人**数值块（同一函数内 `"hp_max": int(round(hp))` 即敌人属性）。

玩家侧**没有**逐回合气血成长；玩家只有休整节点静养恢复上限的 30%（`run.rest_heal_pct = 30`）。
**请不要把「玩家气血会自己涨」计入 D11 的权衡。**
